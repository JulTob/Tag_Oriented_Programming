# Link Forms: ordered Taggings around a Link

> **Proposal only.** This page explains the design recorded by
> [STEP-SPEC-52](../steps/spec/STEP-SPEC-52-ordered-link-underlays.md).
> Released TopKit does not execute this notation yet.

A Relation has two explicit seats:

- `agent`: the Agent whose actual Link receives the call;
- `contact`: the other Agent in that Link call.

Every Relation names them:

```text
@Link(agent, contact)
class Knows(Tag):
    ...
```

Bare `@Link` is not part of the proposed language. Writing the seats makes
the receiver order visible before reading any protocol body.

## Put the ordered Form in the class header

The class header is where TOP already says which Tags run underneath another
Tag. Links use that language too:

```text
@Link(agent, contact)
class Trusts(Network, agent.Knows, contact.Knows, server.Registre):
    ...
```

For `ari.Trusts(ruth)`, read it from left to right:

```text
Network(ruth)
ari.Knows(ruth)
ruth.Knows(ari)
server.Registre(ruth)
ari.Trusts(ruth)
```

| Header entry | Meaning during `ari.Trusts(ruth)` |
| --- | --- |
| `Network` | Apply the ordinary Tag to the Contact: `Network(ruth)` |
| `agent.Knows` | Apply Ari's actual Knows Link to Ruth: `ari.Knows(ruth)` |
| `contact.Knows` | Apply Ruth's actual Knows Link to Ari: `ruth.Knows(ari)` |
| `server.Registre` | Apply that particular Agent's actual Link to Ruth: `server.Registre(ruth)` |

The seat-relative forms always take the opposite seat as their Contact.
That is why `contact.Knows` is the declarative reciprocal Link rather than a
self-Link.

## These are complete, independent Taggings

Each line performs its own Gate, Gainings, Imprints, Field admission, Posts,
diagnostics and recovery before the next line starts. If one turn fails, the
sequence stops where it lands. Earlier completed turns remain completed.

Underlay does not mean shared storage. `Network`, both actual Knows Links,
`server.Registre`, and `ari.Trusts` retain distinct Fields. Every actual Link
also keeps its own Pair. Ripping one does not Rip another.

The syntax resembles a Python base list, but its meaning here is TOP's
ordered Form. It must not create Python member inheritance, shared Link
families, or Pair reuse.

## Relations are blueprints; actual Links are Tags

Bare `Knows` is not a valid header entry. It names a Relation blueprint,
which has no Field to receive an Agent. Name the actual Link instead:

- `agent.Knows` selects the calling Agent's Link;
- `contact.Knows` selects the Contact's Link;
- `server.Registre` selects the Link belonging to a particular Agent.

The lowercase `agent` and `contact` words are symbolic at declaration time.
They resolve afresh for every call. A particular Agent expression is soft as
well: the Relation remembers the Agent and Link coordinate without keeping
that Agent alive, and later resolves the Link currently there.

## Repeated calls stay ordinary

If Ruth is already admitted to `ari.Trusts`, this remains a no-op:

```text
ari.Trusts(ruth)
```

It does not rerun the header because the Relation later gained another
underlay. To request the current Form and training, leave and link again:

```text
del ari.Trusts[ruth]
ari.Trusts(ruth)
```

## Why the tuple spelling was rejected

This is not the language:

```text
@Link(underlays=(Network, Agent.Knows, server.Registre))
class Trusts(Tag):
    ...
```

It turns layering into decorator configuration, duplicates the purpose of
the class header, uses an undeclared uppercase selector, and cannot express
the Contact seat naturally. The explicit-seat Form keeps the Agent, Contact,
order and direction in one place.

## Deployment boundary

The runtime implementation must consume the symbolic header without feeding
it into the old Relation-inheritance and shared-family machinery. STEP-SPEC-22,
its tests, the Specification and the main Links guide must be updated before
this becomes deployed behavior. Until then, treat the examples above as
design notation rather than runnable TopKit code.
