# Guard optional Agent Features

An Agent may legally lack a Feature that another member has. TOP keeps that
absence strict: reading or calling the missing Feature fails. Ask presence
before an optional use:

```text
if "Fireball" @ wizard:
    wizard.Fireball()
```

Read `@` as **at**: “is `Fireball` at this Agent?” The answer concerns the
current Feature binding. It does not call the Action, read the Record's value,
or evaluate whether the eventual act will succeed.

## Presence is separate from value

A present Record may legitimately contain `None`, `False`, zero, or an empty
container. A missing Record has no current binding. Test those questions
separately:

```text
"spellbook" @ wizard      # does the Feature exist here?
wizard.spellbook is None   # what value does the present Record hold?
```

This separation prevents a real `None` value from being mistaken for absence.
It also avoids Python's object-oriented `hasattr` question, which can run
attribute lookup and does not express TOP Feature scope.

## Optional population commands

Guard each member when a population protocol may meet legal specializations:

```text
for wizard in Wizard:
    if "Fireball" @ wizard:
        wizard.Fireball()
```

The guard is explicit and local. A misspelled `Firebal` does not turn into a
silent no-op, and an absent security Feature does not become truthy by default.

If every member must have the Feature, state that in the Contract instead:

```text
@Post
def Has_Fireball(agent):
    return "Fireball" @ agent
```

The Post makes an admitted Agent Broken while that required Gain or Grant is
absent. Sound population walks then omit it under the ordinary Contract rules.

## Deletion and Grant revocation stay strict

[STEP-SPEC-58](../steps/spec/STEP-SPEC-58-agent-feature-deletion.md) proposes
one Agent-level spelling, `del agent.name`, for ending a Gain or revoking that
Agent's Grant to a published Service. The proposal does not replace the
missing Feature with `None`, `True`, or a null Action. Presence becomes false,
and later unguarded use raises the appropriate strict failure.

A Report value already returned is ordinary Python data and cannot be revoked.
A saved public Operation handle is different: it represents a live Grant, so
it rechecks that Grant when called and fails after revocation. Capturing the
handle is not a permanent credential.

The Agency's Service still exists. Ending Ari's Grant to `Dispatch.Send` does
not delete `Dispatch.Send` or Bob's separate Grant.

## Specific failures remain specific

Absence does not flatten TOP's other boundaries:

- a never-managed Python name keeps `AttributeError`;
- an ended TOP Gain or revoked Grant uses its named Resolution Failure;
- a Secret behind a closed composition door remains denied;
- a Constant refuses deletion;
- a Broken or Rogue Agent follows its own access rule;
- an arrested Agent follows Safehouse retry before ordinary acts.

This lets callers distinguish “the Feature is absent” from “the Feature is
present but this Agent may not use it now.”

## Why TOP does not supply a universal neutral value

Python resolves `agent.name` before it knows how the program will use the
result. One value cannot simultaneously be literal `True` in a condition,
literal `None` as data, and a callable that returns `None`. A proxy would also
change `is None`, pattern matching, `hasattr`, `getattr` defaults, awaiting,
iteration, operators, and typo behavior.

[STEP-SPEC-59](../steps/spec/STEP-SPEC-59-neutral-undefined-agent-features.md)
records that exploration and is **Redacted**. TOP already has the smaller,
clearer language tool: check `"name" @ agent`, then use the Feature.
