# Features: what an Agent gains and an Agency serves

> **Vocabulary record under review.** This page records the Director's full
> language for ownership, access, protocols, and conditions. It does not by
> itself change the deployed runtime or clear a STEP. The condition lifetimes
> are staged in [#404](https://github.com/JulTob/Tag_Oriented_Programming/pull/404)
> and [#405](https://github.com/JulTob/Tag_Oriented_Programming/pull/405);
> the Agent-deletion and Grant examples remain proposed language in
> [#390](https://github.com/JulTob/Tag_Oriented_Programming/pull/390).

TOP needs words for three different questions:

1. What does the program expose?
2. Who owns it?
3. What relationship does it establish?

The short reading is:

> A **Feature** is the broad author-facing thing. A Tag gives one Agent a
> **Gain**. An Agency owns a **Service**. Publication gives one Agent a
> **Grant** to that Service. A **Protocol** performs work. Live Posts form
> the **Contract** between an Agent and its Agencies.

Here **Agency** names a Tag in its Field- and Service-owning role. It is not a
second object or an inheritance relationship.

## The complete vocabulary

| Word | TOP meaning |
| --- | --- |
| **Feature** | The broad author-facing term for a named capability, value, check, or shared facility exposed by an Agent or an Agency. |
| **Contribution** | One declaration layer that supplies, composes, replaces, or ends a Feature in the Overlay. This remains the precise composition and implementation word. |
| **Gain** | A Feature given by a Tag to one Agent and owned at Agent scope. Actions, Records (including Tool-marked values), and applied Posts are Gains. |
| **Service** | Work or information owned by a Tag at Agency scope. Reports and Operations are continuing Services. A Pre is a transient Tagging Service. |
| **Grant** | One Agent's authorization and route to a published Service. The Agent receives access, not a copy of the Agency's Service. A Grant can exist while membership, Contract, or arrest rules temporarily block its use; revocation ends it. |
| **Protocol** | An algorithm that may give, use, repair, or remove Features. Running a Protocol does not by itself leave a persistent Feature. A Pre protocol performs a transient Tagging Service. |
| **Contract** | The bond between an Agent and its Agencies, formed by the live Posts that currently bind that Agent. It determines whether the Agent is valid or broken. |

`Grant` is the short TOP word for an Agent's **authorization** to use a
Service. Authorization describes the permission; Grant names the concrete
Agent-to-Service relationship. Whether that Grant may be used *now* remains
a separate membership, Contract, and Safehouse question.

These words do not replace Action, Record, Post, Report, Operation, or the
decorators that declare them. They state ownership and lifetime. For example,
a Report is a Contribution kind, the resulting shared value is an Agency
Service, and `@Public` gives an eligible Agent a Grant to read it.

## How the existing kinds fit

| Declaration or act | Owner after it takes effect | Vocabulary |
| --- | --- | --- |
| `@Action` | one Agent | Gain |
| `@Record`, including a Tool value | one Agent | Gain |
| ordinary `@Post` | one Agent for the life of that Tag membership | Gain and Contract term |
| `@Constant @Post` | one Agent for life once established | uncrushable Gain and lifelong Contract term |
| `@Report` | the declaring Agency | Service |
| `@Operation` | the declaring Agency | Service |
| publication of a Report or Operation | one eligible Agent, pointing to the Agency | Grant |
| `@Pre` | the Agency during one Tagging attempt | transient Tagging Service |
| Imprint, Rip, and repair work | no persistent owner merely because it ran | Protocol |

The distinction matters when categories change. An Action may later be
covered by a Record, but both are still Agent Gains. A Report and an Operation
may share a name across different Tags, but each Service remains owned by its
own Agency. The Overlay decides what is reached; the vocabulary says whose
thing it is.

## A Pre is a transient Tagging Service

```text
class Guild(Tag):

    @Pre
    def Has_Invitation(target):
        return target.invited
```

`Has_Invitation` belongs to `Guild`. The Guild uses that Service while
deciding whether this Tagging may proceed. It does not give the Pre to the
Target, place a Pre layer on the Agent, or leave a Pre behind after the
Tagging attempt.

A Pre therefore cannot crush a same-named Agent Feature. There is no Pre
pile on the Agent. A Pre and a Post may reuse one calculation or one name,
but they establish independent roles: the Pre is a transient Service of the
Tagging; the Post is a Gain that can join the Agent's Contract.

Service and Protocol answer different questions here. *Service* says who the
work serves from and at what scope; *Protocol* says that an algorithm runs.
The Pre protocol performs the Agency's transient Tagging Service, then leaves
no stored Agent Feature.

## A Post is a membership-bound Gain

```text
class Guild(Tag):

    @Post
    def Keeps_Oath(agent):
        return agent.oath_is_kept
```

Both descriptions are true without turning layering into inheritance:

- `Guild` authors and names the responsibility;
- the admitted Agent gains the applied Post;
- the Post binds the Agent while that `Guild` membership exists;
- when that membership ends, the ordinary Post Gain ends with it.

This is how a Post can be Agent-level and still express a responsibility to
a particular Agency. Field membership ties the two scopes together.

A `@Constant @Post` is the deliberate exception. Once established, it is an
uncrushable lifetime term of the Contract. It can remain after the Agent
leaves the Agency, like an NDA that still binds a former employee.

| Condition | Where it belongs | Lifetime |
| --- | --- | --- |
| Pre | Agency Service | only the current Tagging attempt |
| ordinary Post | Agent Gain and Contract term | the corresponding Field membership |
| Constant Post | Agent Gain and Contract term | the Agent's lifetime once established |

## The Contract is the bond

The Contract is not another callable kind and it is not a Service. It is the
relationship formed by all Post terms that currently bind the Agent,
including Constant terms that cannot be hidden by a removable layer.

An adventurer may answer to several guilds; an Agent may belong to several
Agencies. Each Agency can add its own responsibilities. Those live
responsibilities together form the Agent's Contract:

- when every binding Post holds, including when there are none, the Agent has
  a **Valid Contract**;
- when one or more binding Posts fail, the Agent has a **Void Contract**;
- a free Agent with a Valid Contract is a **Valid Agent**;
- a free Agent with a Void Contract is a **Broken Agent**;
- an **arrested Agent** is in a Safehouse while Rip work remains. Arrest is a
  separate cleanup status, so the Agent is neither Valid nor Broken until
  the saved work succeeds.

Older implementation text may say *sound* and *defective* for Valid and
Broken. Those words describe the same population distinction; Safehouse
arrest remains separate.

## Gain deletion, Grant revocation, and Service deletion

The ownership vocabulary makes the intended deletion scope explicit:

```text
del ari.Fireball       # end Ari's Gain
del ari.Dispatch       # revoke Ari's Grant to the Dispatch Service
del Guild.status       # delete Guild's status Report Service itself
```

The second line changes Ari only. It does not delete the Report or Operation
from the Agency and does not revoke another Agent's Grant. A saved or fresh
Agent-bound Service handle must check the Agent's live Grant before use.

Ending an Agent Feature leaves that name absent. It does not expose an old,
already-ended Feature and it does not turn absence into a visible `None`,
`True`, or null Action. A genuinely new Gain or Grant may establish the name
again. Optional code asks first:

```text
if "Fireball" @ wizard:
    wizard.Fireball()
```

Presence is separate from value: a present Record may legitimately contain
`None` or `False`.

These `del agent.name` and Grant rules are the language being designed in
[PR #390](https://github.com/JulTob/Tag_Oriented_Programming/pull/390); they
are not claimed as deployed behavior by this page.

## Reading the model

Use these questions when a design becomes unclear:

- **What does the program expose?** A Feature.
- **Which declaration built this Overlay layer?** A Contribution.
- **What did this Agent receive?** A Gain.
- **What does the Agency own and perform for others?** A Service.
- **Why may this Agent reach that published Service?** It has a Grant.
- **What work runs and then finishes?** A Protocol.
- **What ties the Agent to its Agencies?** The Contract.

`Gate` may still describe a point in the Tagging sequence, but it is not the
ownership category of a Pre. `Clause` is not needed as a TOP category. The
terms here preserve the intended distinction: Pres are transient Services,
Posts are Gains, and the Contract is the bond made from the Posts that bind.
