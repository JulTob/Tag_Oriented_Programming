# Neutral answers from missing Agent Features

> **Proposal — not current TopKit behavior.** This page explains the Brief in
> [STEP-SPEC-59](../steps/spec/STEP-SPEC-59-neutral-undefined-agent-features.md).
> The runtime still raises its current missing-name or access failure until
> that STEP is cleared and implemented.

An Agent may legally stop carrying a Feature, or may never have received a
Feature another Agent carries. A later protocol can still ask for it. For a
game, simulation, or long population command, one optional missing Action need
not end the whole run.

The first proposal gives a **known ended Feature** its neutral answer and
always attempts to emit `MissingFeatureWarning`. TOP remembers the kind of a
Feature deliberately ended by `del agent.name`, or of a Service Grant
deliberately revoked at that name.

| Ended Feature | Proposed answer |
| --- | --- |
| synchronous Action or Operation Grant | a no-op returning `None` |
| coroutine Action or Operation Grant | an empty awaitable whose result is `None` |
| generator or async-generator Action or Operation Grant | an empty iterator of that broad result shape |
| Record, Tool value, or Report Grant | literal `None` |
| directly deleted Contract check | absent in the recommended first stage; direct neutral `True` remains an open choice |

The warning makes the mismatch observable. TOP would call `warnings.warn` on
every neutral use; the application's normal Python warning filter decides how
many diagnostics are displayed. A strict application can promote
`MissingFeatureWarning` to an exception.

## Python cannot choose by the later use

The Director also asked for a neutral answer when no applied Tag ever declared
the requested name:

```text
if wizard.Unknown:         # desired: True
    ...
wizard.Unknown             # desired: None
wizard.Unknown()           # desired: None
```

Python performs `wizard.Unknown` before it knows whether the result will be
tested or called. Literal `None` is false and cannot be called. Literal `True`
is not `None` and cannot be called. Python does not allow a subclass of
`NoneType` that adds these protocols.

A runtime-only total design therefore needs a small missing-Feature value. It
can be truthy and callable, and its call can return literal `None`. The value
itself cannot also be literal `None`: `wizard.Unknown is None`, `case None`,
and exact type checks will distinguish it. It also makes Python `hasattr`
return true and stops `getattr` from using its default.

## The design choices

STEP-SPEC-59 records the full comparison. The practical choices are:

1. **Known coordinates only.** Deliberate deletion and Grant revocation use
   their recorded Feature kind. Never-declared names keep `AttributeError`.
2. **Known coordinates plus a small total fallback.** Exact known kinds keep
   exact neutral results. A never-declared ordinary name receives a truthy,
   callable missing-Feature value. This is the recommended runtime-only route
   if total Agent resolution is required.
3. **Expected-kind declarations.** State that a coordinate is expected to be
   an Action, Record, Contract check or Grant even while absent.
4. **Explicit tolerant syntax.** Keep ordinary lookup strict and make the
   program say when it wants a neutral request.
5. **A TOP source transformer.** Let a translated TOP surface see whether the
   expression is a condition, call or value read. This can produce the exact
   requested literals, but introduces a compiler and tooling boundary.

A propagating null object that absorbs awaiting, iteration, contexts,
operators and chained attributes is also possible. It hides substantially more
mistakes and would stop ordinary calls from returning literal `None`, so the
Brief does not recommend it. Looking at caller bytecode is too brittle; a
global name registry would wrongly couple independent Tags whose names change
Feature category.

No total fallback has been selected or implemented yet.

## Presence still says absent

TOP presence remains the direct question:

```text
del wizard.spellbook

"spellbook" @ wizard      # False: the Feature is absent
wizard.spellbook           # warning; proposed neutral value None
```

Python's `hasattr` follows a different law. It performs the lookup and returns
false only when that lookup raises `AttributeError`. Therefore any missing
Feature that returns a neutral value necessarily makes `hasattr` true:

- for a Record, Tool value, or Report Grant, `hasattr` performs the neutral
  read and attempts to emit the warning;
- for an Action or Operation Grant, `hasattr` captures the null callable and
  returns true; the warning is attempted only if that callable is invoked.

Use `"name" @ agent` for TOP Feature presence. `hasattr` remains Python
reflection and cannot promise the same answer under this proposal.

## A null call keeps its result shape

The deletion ledger would retain the ended callable's declared native form.
A deleted coroutine Action can still be awaited; a deleted generator Action
can still be iterated; each does no domain work and produces its neutral empty
result.

This preserves how the result is consumed. It does not promise that the null
wrapper passes `inspect.iscoroutinefunction` or
`inspect.isgeneratorfunction`. A synchronous function that happens to return
an awaitable dynamically remains classified as synchronous because TOP cannot
infer that behavior safely.

## Access failures keep their meanings

Neutral absence is not a universal exception handler.

- A never-declared spelling remains `AttributeError` under the bounded option;
  a total option must warn and expose its missing-Feature value.
- A Secret behind a closed door remains denied.
- A Constant remains protected against deletion.
- An arrested Agent follows its Safehouse retry rule.
- Membership and a Void Contract can still block a published Service.
- A Broken or Rogue Agent may use its own repair Gains; that does not grant it
  a blocked Agency Service.

A required Feature needs an explicit presence Post:

```text
@Post
def Has_Fireball(agent):
    return "Fireball" @ agent
```

Calling a missing Action only returns `None`; existing condition semantics do
not automatically turn that return value into a failed Post.

## Choices before clearance

1. Select the bounded, hybrid total, declared-kind, explicit-syntax, or
   translated-source design.
2. If the small total value is selected, accept that it is not literal `None`
   and choose its protocols. The recommended minimum supports truth and a
   synchronous call, while keeping awaiting, iteration, contexts, operators,
   subattributes and serialization strict.
3. Decide how a directly deleted Contract name represents the desired split
   between truthy condition use and `None` value use.
4. Confirm exactly when `MissingFeatureWarning` is attempted.
5. Choose whether a saved Operation whose live Grant has been revoked raises
   a Resolution Failure or warns and supplies the selected neutral result. Its
   live recheck is already settled; the saved handle cannot bypass revocation.

The deletion and Grant vocabulary that this proposal builds on is recorded
in [STEP-SPEC-58](../steps/spec/STEP-SPEC-58-agent-feature-deletion.md).
