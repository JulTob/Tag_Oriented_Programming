# Check a Service again before its result leaves

> **Proposal — not current TopKit behavior.** This page explains the Brief in
> [STEP-SPEC-60](../steps/spec/STEP-SPEC-60-service-result-release.md).
> Current TopKit checks a published Report or Operation when access begins;
> it does not yet provide every release check described here.

A public Service answers an Agent only while that Agent has live authority to
use it. Checking before the work begins refuses early and avoids wasted work.
If preparing the answer can change that authority, TOP also needs to ask
again before the answer crosses back to the caller.

The proposed rule is:

1. check before protected work begins;
2. start a fresh check before releasing a result whenever relevant authority
   may have changed;
3. omit the release check only when TOP can prove every authority input stayed
   unchanged.

The release check is fresh. It does not reuse the Post verdict calculated at
entry, because the point is to see changes made while the Service ran.

## What the check asks

For an Agent reaching a published Report or Operation, TOP asks whether:

- the Agent still belongs to the publishing Tag when membership is required;
- its current Contract is Valid;
- any saved Safehouse Rip work can complete; and
- under the proposed Grant vocabulary, this Agent still holds its Grant.

Safehouse retry happens first. If it fails, Arrested Access Failure stops the
act. If it succeeds, TOP checks membership, Contract, and Grant against the
now-free Agent. Their distinct failures do not become one generic refusal.

## An Operation owns its body door

A published Service is public. Its Operation body may still need Secret
Features while it works, so the Agent-facing Action opens its composition
door around that body. The door belongs to the execution of the Operation,
not to its caller.

For a synchronous Operation the proposed boundary is:

```text
check authority
open the Operation body's door
run the body
close the door
start a fresh authority check
release the result only if that check passes
```

The door is closed before a value or control returns to the consumer. A
result prepared inside cannot carry an open composition context with it.

## Reports also have a release boundary

A Report is often a stored Tag value, but a read can execute a descriptor,
metaclass, or other Python code. Even a plain value does not prove that its
Posts stayed true: a Post may read time, an external sensor, or another Agent.

The second check may be skipped only with a real proof about every authority
input. One possible fast path has all of these properties:

- the value is stored and no user code runs during the read;
- there are no visible Posts to re-evaluate; and
- kernel membership, arrest, and Grant state did not change.

“TopKit saw no write” and “no callback ran” are not enough when a Post can
observe state outside the kernel.

Once a Report value has been released, it is an ordinary Python object. TOP
can protect the next read; it cannot revoke a value already copied into a
variable.

## Lazy Operations make every yield a release

A native coroutine or generator can pause after the first access check. The
proposal therefore treats each continuation as a small protected call:

```text
check before resume
open the body door
resume until yield, return, or failure
close the body door
start a fresh release check
release the yielded item or final result only if authority still holds
```

The same rule applies again at the next resume. It includes a generator's
final `StopIteration.value` and a coroutine's awaited result. A wrapper may
change exact reflection such as `inspect.isgenerator`; the declared or TOP
result category must carry that information instead.

The first profile can recognize exact native coroutine and generator objects,
even when a synchronous function returns one. A custom awaitable, iterator,
or stream needs an explicit supported adapter or a clear refusal; TOP cannot
pretend an unknown deferred object is guarded.

Cleanup needs its own answer. Closing, cancellation, `GeneratorExit`, and
`finally` may need to release resources after authority disappears. The Brief
recommends allowing cleanup with no value release, but whether it uses the
ordinary body door, a narrower door, or waits for Safehouse recovery remains
open.

## Saved handles stay live; returned values do not

A saved public Operation handle represents a live route to a Service. It must
check current authority when called and through every supported continuation.
A saved `Tag[agent]` view should resolve the same live Agent state.

An ordinary Action callable and an already-returned Report value follow their
separate Python capture laws. This proposal does not erase objects already
delivered to user code.

## One Agent, one thread

The proposal uses TOP's current one-Agent, one-thread execution profile. Async
tasks can interleave at suspension points, so every continuation is checked.

In a shared-Agent or free-threaded profile, another thread could change
authority after the last check and before Python hands over the object. A
second unlocked check cannot close that race. Such a profile needs
synchronization spanning the check and release and belongs in another STEP.

## Six choices before clearance

1. Generalize the Safehouse continuation proxy into one composable guard, or
   layer a Service guard around it.
2. Identify the Report paths that can prove every authority input stable.
3. Refuse native async generators in the first profile, or guard their whole
   `async for`, `asend`, `athrow`, and `aclose` protocol.
4. Choose the public introspection that reports the original callable shape
   after TOP returns a lazy proxy.
5. Let cleanup run after authority loss, and decide whether it receives the
   ordinary body door, a narrower cleanup door, or waits for recovery.
6. If the body raises after authority disappears, choose whether the authority
   failure hides the protected exception payload or compatibility keeps the
   body exception primary.

Until STEP-SPEC-60 is cleared and implemented, application code that needs
this boundary must perform its own final authority check immediately before
releasing protected data.
